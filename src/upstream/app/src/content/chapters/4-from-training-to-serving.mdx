<Fragment set:html={"<h2 id=\"s-4\">4. From training to serving</h2>\n<p class=\"full\">A model is trained once, but it is served for as long as anyone uses it. So far, this handbook has been about the first part: getting an MoE to train fast and well. This chapter is about the second.</p><p class=\"full\">Serving judges the model by different numbers. A training run is measured in step time and in loss; a serving system is measured in how quickly each request gets its answer and in how many GPUs it takes to answer them all. The model is the same in both, but the goals are not, so some choices that were right for training deserve a second look once the run is over.</p><p class=\"full\">An MoE has more to revisit than a dense model. Each token runs through only a few experts, yet every expert is usually kept in memory in case some token picks it, so the model is cheap in compute per token and expensive in memory. Once requests are decoded one token at a time, each expert also sees only a few tokens per step, which makes the number of GPUs the experts are spread over a serving decision of its own. Attention and the experts, which share each GPU in the layout used so far, make different demands on the hardware as well.</p><p class=\"full\">This chapter takes those differences one at a time. We start with k, the size of the expert set the router picks for a token. Next, we look at how much memory the experts take, how many GPUs to spread them over, and where attention and the experts should run. We end with RL post-training, where a serving engine writes the samples a trainer learns from, and the two can disagree on which experts each token went through.</p>\n\n<p class=\"full\">The first of these changes is a single number you set at serving time. If you serve each token with a different number of experts than it was trained with, what happens to its output?</p>\n<h3 id=\"s-4-serving-a-different-k\">Serving a different k</h3><p class=\"full\">Training fixes how many experts each token uses, but nothing stops you from serving fewer. Each routed expert you drop from a token&#x27;s top k is compute saved, while every expert stays resident for the tokens that do pick it, so memory does not change<sup data-k=\"kcut-cost\"><a href=\"#ref-2609.04575\" data-footnote-ref=\"\">243</a></sup>. The difficulty lies in the routing weights. A router that renormalizes (<a class=\"xref\" href=\"#s-3-1\">3.1</a>) divides the chosen experts&#x27; probabilities by their sum, so the scale of the expert branch&#x27;s output, its gain, is set for the trained k. When you serve fewer experts, the survivors share that same total among themselves, and each one gets a larger weight than it had at the trained k. A smaller k therefore changes two things at once: which experts run, and how much each one contributes.</p><p class=\"full\">Chen and Yao separate those two effects with one integer. They keep the top k1 experts but divide their weights by the softmax mass of the top k2, chosen at serving with no training. Setting k2 = k1 is the usual renormalization over the survivors, which LExI, a method that picks a different k for each layer, also uses<sup data-k=\"lexi-gate\"><a href=\"#ref-src-lexi-gate\" data-footnote-ref=\"\">244</a></sup>, setting it to the number of experts removes renormalization, and setting it to the trained k anchors the gain to the value the model was trained with.</p><p class=\"full\">The figure below routes one simulated token through a softmax shaped like the router of Qwen3.6-35B-A3B, 256 routed experts trained at top-8, and serves it at smaller k, with one row per denominator. Follow the middle panel as k falls: over the survivors, each served expert weighs more than at top-8; over the trained top 8, it keeps its trained weight; over the top 16, it weighs less. The right panel gives the MMLU change measured for each row.</p>"} />
